# Hy4-flash on 2x R9700: where it stands (2026-11-21)

The test machine: 2x AMD Radeon R9700 (gfx1201, 32 GB each, PCIe Gen5 x8), Ryzen 7 7700, 64 GB RAM,
tensor parallel 2 (llama.cpp: layer split), power cap 330 W, NVMe <= 50 °C at the start of each
prefill run. radiance numbers come from a throughput bench against the HTTP API (`bench_throughput`,
256 generated tokens a request, and a fixed-prompt prefill run); llama.cpp's are `llama-bench`.

| | prefill ~4-6K (tok/s) | decode, 1 client (tok/s) | decode 4 / 8 clients (tok/s) |
|---|---|---|---|
| llama.cpp, PR #32517, AngelSlim Q4_K_M, 19 expert layers on the cards, 22 on CPU, `-ub 2048 -fa 1` | 360 | 13.75 | — |
| radiance 2.2.0 + these plugins (final: fusions, split `hc_pre`, E4M3 Engram), no speculation | 3,036 | 57.7 | 196.2 / 360.6 |
| the same with the DFly2 drafter (`docs/DFLY2.md`), adaptive window, `RADIANCE_AQL_CHAIN_FENCE=1` | 2,976 | 109.8 | 341 / 425-603 (varies run to run on 2.2) |
| Qwen3.8-Flash-Next on the same cards (all weights in VRAM) | ~6,400 | 201 | 581 / 972 |

The gap to llama.cpp is mostly placement: Hy4-flash does not fit in 64 GB of VRAM. llama.cpp keeps
the experts of 22 layers on the CPU and reads the Engram table (`per_layer_token_embd`, 59 GiB E4M3)
through mmap; radiance tiers the experts between VRAM and pinned host memory (`expert_tiered`) and
reads the n-gram table through libavx's row cache with read-ahead. llama.cpp's default micro-batch
(512, no flash attention) gave 174 tok/s of prefill and 13.5 of decode.

Published llama.cpp numbers for the same GGUF on other hardware (AngelSlim's model card): Mac M5 Max
128 GB, Q4_K_M: prefill 630 / 448 / 419 tok/s at 4K / 16K / 32K, decode 48 / 45 / 44; RTX Spark
128 GB, SPARK-4Bit-Fast: prefill 799 / 717 / 707, decode 32 / 33 / 33.
